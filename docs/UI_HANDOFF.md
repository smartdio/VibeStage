## 当前状态与保存机制

控制 HUD 中的调整属于临时 PilotCamera。点击“应用机位”将 patch 合并到实际物理机位 ID 的手动草稿；取消不保留此次临时调整。应用成功不等于已写入磁盘，还要点击“保存工作区”。

“保存工作区”顺序调用保存机位／分镜，再保存交付资料；不是跨文件原子事务。机位失败则不继续保存交付，机位成功后交付仍可能失败。音轨使用自己的保存按钮。页面需明确呈现哪个阶段成功，不能只凭按钮点击判断已保存。

手动机位文件为 `projects/<project>/settings/<scene>.camera.json`，覆盖匹配的代码字段。用户现有设置和 `delivery.json` 必须保留。共享同一物理机位的多个镜头会共同受到修改。

## 建议的新对话工作顺序

先确认用户调整的是哪个项目、镜头，使用画面内控制还是下方数值输入，以及哪项操作看不出效果。如果用户当前浏览器能直接提供这些信息，优先检查现状，不先要求用户重复说明。

选一个可逆测试场景或项目副本，固定同一镜头和时间，做明显但合理的位置／朝向／焦距变化。依次对比调整前、控制中、应用后、再次播放／seek 后、保存并重新加载后的实际帧，同时记录物理 cameraId、分镜 ID、patch 和设置文件。分别验证取消不落地、应用落草稿、保存后重载保持，以及共享机位与预设机位。

重点区分“手动输入没有进入控制器”“临时画面变了但应用后回退”“代码更新覆盖了设置”“实际编辑的机位与正在观看的镜头不同”“草稿未保存或保存失败”“预设只打开参数区”和“改变太小／反馈不明确”。这些都是排查方向，目前没有确认哪一项是根因。

再据证据改交互。可能需要更明确的控制状态、当前目标、即时数值／画面反馈、应用结果、未保存提示和调整前后对比；不要未经复现就堆叠新面板。用户核心诉求是容易手动调整，并能确认调整真实生效。
